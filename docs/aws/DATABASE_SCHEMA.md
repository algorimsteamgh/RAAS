# RAASHiring database schema (PostgreSQL 16)

Database `raas` on RDS `raas-prod`, schema `public`. The schema is created and
changed only by Alembic migrations in `backend/app/db/migrations/` (run by the
one-off `migrate` ECS task: `python -m backend.app.db.migrate`). Current head:
`0002_batch_files`.

Table and column names are the same as in the SQLite database, so the data
load maps 1:1 and validation tools (Liftproof) can compare them by name. Type
mapping: SQLite TEXT holding JSON → `jsonb`; INTEGER AUTOINCREMENT → `bigint
GENERATED BY DEFAULT AS IDENTITY`; TIMESTAMP → `timestamptz` (UTC); REAL →
`double precision`.

## Tables

### candidates (PK candidate_id)
| column | type | notes |
|---|---|---|
| candidate_id | text PK | `CAND-XXXXXXXX` |
| full_name, email, phone, location | text | |
| roles, skills | jsonb | arrays of strings |
| years_experience | double precision | |
| notice_period | text | |
| source | text | `UPLOADED`, `MOCK` (seed data), ... |
| status | text | default `COMPLETED` |
| raw_json | jsonb | full extraction returned by the API |
| file_hash | text | SHA-256 of the original CV |
| filename | text | |
| created_at | timestamptz | |

### original_files (PK candidate_id) — the CV key
| column | type | notes |
|---|---|---|
| candidate_id | text PK | |
| filename | text not null | |
| file_type | text not null | `pdf`, `docx`, `txt`, ... |
| sha256_hash | text not null unique | hex SHA-256 of the file |
| **s3_key** | text not null | **new**: object key in the CV bucket, `cvs/{candidate_id}/{sha256_hash}.{file_type}` |
| size_bytes | bigint | **new** |
| created_at | timestamptz | |

The SQLite `file_data` BLOB column is gone: the bytes live in S3 bucket
`raas-cvs-007477962703-ap-southeast-1` (SSE-KMS, versioned). Each object also
carries the SHA-256 as its S3 checksum (`ChecksumSHA256`, base64).

### match_results (PK id, unique candidate_id + job_id)
id bigint identity, candidate_id text, job_id text, score double precision,
recommendation text, matched_skills jsonb, missing_skills jsonb, reasoning
text, score_breakdown jsonb, created_at timestamptz.

### jobs (PK job_id)
job_id, title, department, location, employment_type, seniority, description
(text); minimum_years_experience double precision; required_skills,
preferred_skills, education_requirements, domain_requirements,
responsibilities (jsonb arrays); other_constraints, source, status (text);
created_at, updated_at (timestamptz).

### recruiter_actions (PK id)
id bigint identity, candidate_id, job_id, action, note, tag, user_id (text),
created_at timestamptz.

### candidate_chat_messages (PK id)
id bigint identity, candidate_id text **FK → candidates ON DELETE CASCADE**,
job_id, role, content (text), created_at timestamptz.

### audit_logs (PK id)
id bigint identity, event_type, candidate_id, details (text), "timestamp"
timestamptz (quoted: the column is named `timestamp`).

### batch_jobs (PK batch_id)
batch_id, job_id, status (text); total, completed, processing, queued,
failed (integer); file_statuses jsonb; created_at, updated_at. Counters and
file_statuses are recomputed from batch_files.

### batch_files (PK batch_id + file_index) — new, not in SQLite
batch_id FK → batch_jobs, file_index, filename, file_type, staging_key
(`batch/{batch_id}/{file_index}.{ext}` in the CV bucket until processed),
size_bytes, status (`QUEUED`, `PROCESSING`, `COMPLETED`, `SKIPPED`, `FAILED`),
candidate_id, error, attempts, created_at, updated_at.

## Indexes
`ix_candidates_source`, `ix_candidates_created_at`,
`ix_audit_logs_candidate`, `ix_match_results_job_score`,
`ix_recruiter_actions_candidate`, `idx_chat_cand`, `ix_batch_files_status`.

## Comparing with SQLite (for validation)
- Row counts per table are equal, except where the seed-data rule
  (`--exclude-source MOCK`) is applied; `batch_files` has no SQLite source.
- `original_files`: compare `candidate_id, filename, file_type, sha256_hash,
  created_at`; check the CV with `sha256(S3 object at s3_key) == sha256_hash ==
  sha256(SQLite file_data)`.
- JSON columns: compare parsed values, not text (jsonb reorders keys).
- NUL characters (`\x00`) cannot be stored in PostgreSQL text/jsonb and are
  removed; the load report lists the affected rows.
- The load job's own report (`backend/app/dataload`) does all of these checks.
